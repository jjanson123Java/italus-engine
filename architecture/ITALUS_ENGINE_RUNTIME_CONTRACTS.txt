PURPOSE
-------
This document defines the runtime contracts for the Italus Book Engine. It is not a project management file. It is an interface and data-contract 
specification that locks how requests, manifests, prompts, validation context, AI responses, controller payloads, and commit payloads move through 
the engine at runtime. Its purpose is to prevent implementation drift between project_runner.py, prompt_builder.py, ai_runner.py, frontend/controller 
layers, canon packet assembly, Guardian Engine, and post_generation_canon_validator.py.

WHAT "RUNTIME CONTRACTS" MEANS
------------------------------
A runtime contract is the expected shape, meaning, and validation rule for data exchanged between components while the engine is running.

Examples:
- what fields a generation request must contain
- what packet metadata must be emitted
- what a validator response must look like
- what severity levels mean
- what lifecycle state a request is in
- what a controller-facing UI payload should expose

This is different from project planning.
A project management file tracks milestones, phases, owners, and schedules.
A runtime contracts file defines executable interface boundaries.

NON-NEGOTIABLE ARCHITECTURAL RULES
----------------------------------
1. Book pack canon and compressed book pack canon are the same artifact.
2. Canon Packet Engine validates packet assembly/integrity.
3. Guardian Engine validates request legality before generation.
4. post_generation_canon_validator validates generated prose after generation.
5. Prompt Builder serves the model; validators must not depend on prompt parsing for truth.
6. project_runner.py is the orchestrator and payload hub.
7. Accepted local continuity outranks weaker runtime inference.

AUTHORITY ORDER
---------------
Validation and continuity resolution should prefer:
1. accepted local continuity
2. explicit request metadata
3. book pack canon
4. global canon
5. heuristics only if stronger layers are unavailable

SEVERITY FRAMEWORK
------------------
All validators should use a shared severity model.

ERROR
- hard failure
- generation or commit must stop

WARNING
- generation may continue
- commit may continue unless a later rule blocks it
- UI should display warning

INFO
- diagnostic only
- no blocking behavior

Severity examples
- ERROR: tree speaks directly
- ERROR: unsupported AI provider
- ERROR: malformed packet manifest
- WARNING: scene type underused or continuity risk
- INFO: fallback provider default selected

Field rules
-----------
book_id
- string
- must reference an active manifest book

chapter_id
- string
- must belong to the selected book

event_id
- string
- primary event selector if present

event_name
- optional if event_id is present
- project_runner may resolve it from event_id

year
- integer preferred
- may be autofilled from event defaults or event index

guardian
- string
- may be autofilled from canonical event/manifest context

scene_type
- string
- must come from allowed scene types manifest or later guardian validation

callback_scene_ids
- array of scene_id strings
- defaults to empty list if absent

ai_provider
- defaults from app settings if absent

Consumers

- post_generation_canon_validator

Purpose
- normalize provider execution results

Current implementation reality
------------------------------
Current ai_runner.py exposes provider capability metadata and dispatches by provider id.
Current dispatch returns raw text on success and raises exceptions for invalid/unimplemented providers.
Runtime orchestration should normalize that into the following contract.

Normalized schema
-----------------
{
  "runtime_contract_version": "1.0",

  "ai_provider": "claude",
  "ai_status": "ok",
  "ai_error": null,

  "generated_text": "Generated prose here...",
  "raw_response_available": false,

  "generation_state": "ai_generation_completed"
}

Allowed ai_status values
------------------------
- ok
- provider_invalid
- provider_not_implemented
- generation_error

Rules
-----
- generated_text may be empty on failure
- ai_status != ok blocks post-generation prose validation except optional diagnostic modes
