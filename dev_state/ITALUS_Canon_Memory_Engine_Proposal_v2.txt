WHY THE CANON MEMORY ENGINE IS NEEDED
-------------------------------------
AI generation alone is not sufficient for long-form narrative continuity.

Without a Canon Memory Engine:
- the model can validate rules only within the prompt it receives in that moment
- prior accepted scenes can drift out of active context
- duplicate scenes can be detected inconsistently
- chapter and book progress can be forgotten between sessions
- generated prose can be mistaken for canon before approval

The Canon Memory Engine solves this by turning continuity from a prompt-only behavior into a managed system.

It ensures the engine can answer:
- What should be loaded before generation?
- What chapter memory is currently active?
- What book memory is currently active?
- Is this request a continuation or a new branch?
- Does this request duplicate an earlier accepted scene?
- What state should be updated after acceptance?
- What should become canon and what should remain only candidate prose?

This distinction is central to the Italus project.

STATIC CANON VS DYNAMIC MEMORY
------------------------------
The Italus system uses two different but complementary forms of continuity control.

1. Static Canon
These files define what is true in the world:
- world bible
- generation engine rules
- timeline drift detector
- historical interaction maps
- canon packs
- manifests

Static canon answers:
- What is allowed in the story world?
- Which guardians, events, and timelines are valid?
- What cannot be contradicted?

2. Dynamic Memory
These files track what this project has already generated and accepted:
- book_state.json
- chapter_continuity_digests.json
- scene registry / accepted scenes
- backup snapshots

Dynamic memory answers:
- What was the last accepted scene?
- What is the active chapter state?
- What is the current book state?
- What local continuity needs to be injected right now?

The Canon Memory Engine is the system that connects static canon and dynamic memory.

FILE ROLES VS MEMORY ENGINE BEHAVIOR

The file roles alone do not solve continuity.

Example file roles:
- book_state.json stores last known state at the book level
- chapter_continuity_digests.json stores summarized chapter continuity

Those are storage responsibilities.

The Canon Memory Engine is different.
It is the operational behavior that decides how those files are used.

Behavioral flow:
    request
      -> memory lookup
      -> context assembly
      -> prompt building
      -> AI generation
      -> author review
      -> save validation
      -> memory update

That is why the Canon Memory Engine matters.
It turns files from passive storage into active continuity memory.

HYBRID MODEL: AI VALIDATION + ENGINE MEMORY
-------------------------------------------
The correct Italus design is hybrid.

Layer 1 — AI-side canon validation
The AI model must still receive canon materials and validate before writing.
This includes:
- drift detector rules
- generation engine rules
- world bible constraints
- historical interaction constraints
- canon packet documents

The AI should:
- detect canonical contradictions
- detect duplicate or near-duplicate scene intent
- stop generation when canon conflicts exist
- ask the author whether to continue, take a new angle, replace, or cancel

Layer 2 — Engine-side memory orchestration
The Python engine should decide:
- which continuity files to load
- which scene history to scope
- what memory slice belongs in the prompt
- what happens after save
- what becomes canon
- how continuity files are updated

This is not either/or.
It is:
    engine memory layer + AI validation layer

That is the strongest design.

HOW THE ENGINE PREVENTS TIMELINE DRIFT
--------------------------------------
Timeline drift is prevented through multiple defenses.

Defense 1 — Truth Layer
The canon documents define non-negotiable facts:
- valid guardian periods
- historical event years
- geographic plausibility
- Italus biology and communication rules
- book range compatibility

Defense 2 — Active Memory Layer
Before generation the runner loads:
- chapter digest
- book state
- event-scoped scene history
- duplicate candidates
- resume or re-anchor mode

This prevents local continuity loss.

Defense 3 — Structural Validation Layer
The runner checks:
- exact duplicate candidates
- continuation parent validity
- callback references
- event and chapter scope
- same-book/same-event structural rules

This prevents invalid narrative linking.

Defense 4 — AI Reasoning Layer
The model still evaluates:
- thematic duplication
- implied contradiction
- tone mismatch
- character reaction mismatch
- conflict with canon packet constraints

This catches issues that structural rules alone may miss.

Defense 5 — Controlled Commit Layer
Generated prose does not become canon automatically.
It becomes canon only after:
- author review
- acceptance
- save validation
- digest update
- book state update
- scene registry update
- backup creation

This prevents accidental canon corruption.

WHY THIS SUPPORTS THOUSANDS OF SCENES
-------------------------------------
A large saga cannot keep all accepted narrative state inside the active model context window.

The Canon Memory Engine scales by:
- summarizing chapter continuity rather than replaying full chapter text
- tracking book-level state separately from chapter-level state
- keeping accepted scene history structured and searchable
- scoping duplicate checks to relevant continuity ranges
- loading only the memory slice needed for the current request

This keeps the active prompt smaller while preserving continuity.

In effect:
- static canon stays authoritative
- dynamic memory stays current
- the AI receives only the most relevant packet for the next scene

This is how the engine can support very large narrative systems.
